## Defect report
- Title: Defect 1 – Excluding all three tools makes `POST /api/pizza` fail with 500 and an empty body
- Request:
  `POST https://quickpizza.grafana.com/api/pizza` with header `Authorization: token <token of a logged-in user>` and body `{"excludedTools": ["Knife", "Pizza cutter", "Scissors"]}`.
  With curl: `curl -i -H "@auth.txt" -d "@no_tools.json" https://quickpizza.grafana.com/api/pizza`
- Expected result: No pizza can be cut without a tool, so the request cannot be satisfied. The product owner says it must get status **400 Bad Request** with a JSON error message, for example `{"error": "no tool left to cut the pizza"}`.
- Actual result: Status **500 Internal Server Error**, `content-length: 0`, no `content-type` header and an empty body. Excluding 0, 1 or 2 tools works (200 with a pizza whose tool is not excluded).
- Severity: **Medium**. Nothing is lost or exposed, and the input is unusual, but the server crashes on valid JSON from a client, and the empty body gives the calling app nothing to show the customer, who cannot tell what went wrong or how to fix the request. A 5xx also looks like an outage in monitoring.

## Part B
1. **Failures that only a real server shows.** (a) Integration and deployment failures: the load balancer sending requests to a server that does not know the user (Step 0.12), a wrong route, a missing or wrong header such as `content-type`, or the crash with an empty body in Defect 1, which comes from how the web layer handles an error, not from one function. (b) Failures in the data and the real dependencies: data that is not stored or not read back (a rating that cannot be read after it was saved), the database refusing a value, or the real JSON decoder of the server (the Go `cannot unmarshal` messages) behaving differently from what a stub would pretend. Stubs only answer what the tester wrote into them, so they cannot show either kind. **Reason for unit tests as well:** they are fast, run without a network and without shared data, and point to the exact function that broke, so they can try many inputs (every edge of the star rule, every error branch) cheaply and run on every save; an API test that fails only says that something somewhere in the stack is wrong, and can also fail because the network or the site is down.

2. **Own user per test.** Ratings made with the public token belong to everyone who practises on QuickPizza. Another student could change or delete them while my test runs, so my test would fail for no fault in QuickPizza (or pass wrongly), and my tests would change other people's data, which the rules forbid. A new user with a random name starts with no ratings, so each test knows exactly what is there, is independent of the other tests and of the order they run in, and touches only data it created. **In Project 2** each test (through a fixture) will create its own customer account / cart / booking on the shared shop or hotel, with a unique made-up name such as `lab-<uuid>`, use only the token or `Cart-Token` that this account gets back, and delete what it created after the test (`yield` fixture), never touching the data of other groups. The group's password or API key comes from an environment variable, not from the code.

3. **One session.** QuickPizza runs on several servers behind a load balancer, and each server keeps its own users. The first answer sets the `AWSALB` cookie, which tells the load balancer which server to use. A `requests.Session` keeps that cookie and sends it back with every request, so the user is created, logs in and makes ratings on the same server. Without it, each `requests.post` is on its own, and the login may reach a server that has never seen the user. One session for the whole run (`scope="session"`) also reuses the connection, which is faster. **Step 0.12:** I ran `pytest -v test_no_session.py` three times and it **failed all three times** with `assert 401 == 200` on the login: the user was created (201) but the login went to another server. In the lab authors' tries it failed 46 times out of 49, so it is a flaky test that can sometimes pass; I deleted it.

4. **Block that revealed the defect:** "all three tools excluded" (`["Knife", "Pizza cutter", "Scissors"]`). The original inputs were both in the block "one tool excluded", so they could not find it. **500 with an empty body is worse than 400 with a message** because a 500 says the server failed, not the client, so an app may retry the same request again and again or show a generic "server error"; with no body it cannot tell the user what was wrong or what to change. A 400 with a JSON message says the request itself cannot be served, so the app stops retrying and can show the message ("you excluded every tool") and let the user fix the input. **Why `xfail` instead of deleting:** the test describes the correct behaviour and documents a known defect. With `xfail` the rest of the suite stays green, but the defect stays visible in every run and in the report. With `strict=True`, as soon as QuickPizza fixes the defect the test passes unexpectedly and the run fails, telling us to remove the mark so it becomes a normal regression test. Deleting it would hide the defect and lose the check.

5. **Base choice coverage** needs one base test plus, for each characteristic, one test per non-base block: 1 + (3 − 1) + (4 − 1) + (2 − 1) + (3 − 1) = 1 + 2 + 3 + 1 + 2 = **9 tests** (C1 has 3 blocks, C2 has 4, C3 has 2, C4 has 3). **All combinations coverage** needs one test for every combination of blocks: 3 × 4 × 2 × 3 = **72 tests**. `test_create_rating.py` holds exactly the 9 tests.

6. **Step A4 codes:** read → **404** `{"error":"not found"}`; change → **400** `{"error":"rating ID <id> not found"}`; delete → **400** `{"error":"rating ID <id> not found"}`. **Expected:** read 404 is what I would expect (or 403); for a resource that belongs to someone else, 404 is a good choice because it does not even tell the other user that the rating exists. For change and delete I would expect the same **404** (or 403), because the rating is "not found" for this user, exactly as the error message itself says. **Is the difference a defect?** The security rule holds — the other user cannot read, change or delete the rating, and the owner's rating is unchanged — so it is not a security defect, and my tests (any 4xx) pass. It is a **minor consistency defect**: 400 means "your request is malformed", but the body `{"stars": 1}` is valid; the message says "not found" while the code says "bad request", and the same situation gives 404 on GET and 400 on PUT/DELETE. A client that handles 404 to mean "gone" will treat these differently. Low severity.

7. **Made-up token.** `curl -H "@madeup.txt" https://quickpizza.grafana.com/api/ratings` with `Authorization: token 0000000000000000` answered **200** with `content-type: application/json` and a list of 50 ratings (`{"ratings":[{"id":1,"stars":5,"pizza_id":1}, ...]}`), almost the same list that the public token `abcdef0123456789` gets. A token of 15 characters gets 401, so QuickPizza seems to accept **any token of 16 characters** without checking that it was ever issued by a login, and treats it as the shared default user. **This is a defect** (a broken authentication / authorization defect) on a real system, even if it is a deliberate demo shortcut on QuickPizza: the server must accept only tokens it issued, and reject the rest with 401. A stranger who knows the token length could, without any account or password, read the ratings (and, on a real system, the personal data, orders or payment details) of that user, and could also create, change or delete data in that user's name; with guessing they might hit tokens of real users. I only read with this token and changed nothing.

8. **API test vs web page test.** An API test checks better the **rules and error handling on the server itself**: it can send inputs that the web pages never let a user send (stars = 0 or 6, `"3"` as text, a missing field, a wrong token, another user's rating id) and check the exact status code and JSON body, quickly and without a browser; this is how it found Defect 1 and the made-up token problem, which a form with a 1–5 star picker would hide. **Only a test through the web pages** can check what the user actually sees and does: that the page shows the pizza and the error message correctly, that buttons, layout, JavaScript and the flow between pages work in a real browser, and that the result of a request is displayed to the user (for example, that a 500 does not leave a blank screen).
